
好问题。这涉及 Node.js 的一个根本限制。核心原因一句话：Node.js 的 JavaScript 执行是单线程的，cluster 让你把一个 CPU 核心的性能扩展到全部核心。

为什么要有 cluster？
Node.js 的主执行是单线程的——一个进程只跑一个 JS 主线程。哪怕你的服务器有 8 核 CPU，一个普通 Node 进程也只能用满 1 个核，剩下 7 个核闲置。

cluster 的作用就是：fork 出多个工作进程（每个进程一个独立的 V8 实例 + 事件循环），让它们一起监听同一个端口，把请求分摊到所有 CPU 核心上。

    ┌─────────────────┐
                  │  Primary 主进程   │  ← 不处理请求，只做管理
                  │  (监听/分发)      │
                  └────────┬────────┘
                           │ fork()
        ┌──────────┬───────┼───────┬──────────┐
        ▼          ▼       ▼       ▼          ▼
   ┌────────┐ ┌────────┐      ┌────────┐ ┌────────┐
   │Worker 1│ │Worker 2│ ...  │Worker 7│ │Worker 8│  ← 真正处理HTTP请求
   │ :8000  │ │ :8000  │      │ :8000  │ │ :8000  │
   └────────┘ └────────┘      └────────┘ └────────┘
     核心1      核心2            核心7      核心8
Primary 和 Worker 的关系
Primary（主进程）	Worker（工作进程）
数量	1 个	通常 = CPU 核数
职责	管理：fork、监控、重启 worker	干活：真正处理 HTTP 请求
是否处理请求	❌ 不处理	✅ 处理
代码分支	cluster.isPrimary 为 true	else 分支
关键点：

1. 它们是完全独立的进程，不是线程。
   每个 worker 有自己独立的内存、V8 实例、事件循环。它们不共享变量——如果你在 worker 里用一个全局计数器，8 个 worker 就有 8 份互不相干的计数器。要共享状态得靠外部（Redis、数据库）或进程间通信（IPC）。
2. 为什么它们能同时监听 8000 端口？
   正常情况下两个进程 listen 同一端口会报 EADDRINUSE 错误。cluster 里能共存，是因为其实只有 Primary 真正绑定了 socket，然后由 Primary 把连接分发给各个 worker（默认用轮询 round-robin 策略）。worker 里的 listen(8000) 是被 cluster 模块"劫持"过的，不是真的独立绑定。
3. 父子关系带来的容错。
   Primary 通过 IPC 通道监控每个 worker。这就是我们加的：

cluster.on('exit', (worker) => {
  cluster.fork(); // 某个 worker 崩了，立刻补一个新的
});
单进程模式下，进程一崩服务就全挂了；cluster 模式下，一个 worker 崩溃只影响它当时正在处理的那几个请求，其它 worker 照常服务，Primary 还能马上重启它。高可用。

一句话总结
cluster 存在的两个理由：

利用多核 —— 突破 Node 单线程只能用 1 核的限制，吞吐量近似翻倍（×核数）。
高可用 —— Primary 守护 worker，崩了自动重启，单点故障不影响整体。
Primary 是"包工头"（只管理不干活），workers 是"工人"（干活但互相独立）。

补充：现代生产环境里，很多人用 PM2 的 cluster 模式，或者直接用 Docker/K8s 起多个容器，来替代手写 cluster 代码——原理完全一样，只是把这套 fork + 重启 + 负载均衡的逻辑封装好了。
